# Анализ безопасности и производительности MyApp

Дата: 12 октября 2026 года. Проверена текущая рабочая копия Vue/Vite, ASP.NET Core 10, EF Core/Npgsql, сервисы авторизации, документы и склад, медиахранилище, инициализация БД и CI. Код приложения не изменялся.

Это статический аудит с проверкой сборки, существующих тестов и зависимостей. Боевой сервер, реальные аккаунты, настройки reverse proxy, права PostgreSQL и боевые данные не проверялись. Условия воспроизведения ниже выведены из кода; разрушительные запросы не выполнялись. Оценки производительности требуют подтверждения профилированием на тестовой копии данных.

Приоритеты: P1 — исправить прежде всего; P2 — следующий этап; P3 — улучшение сопровождения и эффективности. «Условный риск» означает, что последствия зависят от конфигурации или бизнес-правил.

## Безопасность

### S1. P1 — обход прав отдельных таблиц через регистр имени

Место: `src/MyApp.API/Controllers/TableViewController.cs:28`; `src/MyApp.Application/Services/TableViewService.cs:11,56`.

Контроллер выбирает требуемое право через регистрозависимый `switch`. Сервис разрешает имена без учёта регистра и затем переводит их в нижний регистр. Пользователь с `menu.tables`, но без `tables.v_workers`, получает отказ на `/api/tables/v_workers`, однако имя `V_WORKERS` даёт `requiredPermission = null` и проходит к разрешённому представлению. Это распространяется и на складские таблицы.

Исправление: сначала нормализовать имя, затем выбрать право; неизвестные имена отклонять. Проверять права в одном месте до чтения данных. Регрессионные проверки: нижний/верхний/смешанный регистр каждой таблицы для аккаунта с одним разрешённым разделом.

### S2. P1 — детальные права транспорта защищают интерфейс, но не все API

Место: `src/MyApp.Application/Security/Permissions.cs:21`; `src/MyApp.API/Controllers/VehicleController.cs:20,90,283,313`; `src/MyApp.Application/Services/VehicleService.cs:295`.

Каталог содержит `vehicles.hours`, `vehicles.works`, `vehicles.report`, `vehicles.parts_request`, `vehicles.repair_request`. На контроллере требуется только `menu.vehicles`. В частности, добавление/импорт моточасов и чтение полного repair-journal не требуют соответствующих детальных claims. Проверки профессии и автора в отдельных сервисах полезны, но не заменяют права на действие. `Permissions.Expand` добавляет родительское право при выдаче любого дочернего, поэтому аккаунт с единственным доступом к отчётам также проходит общую политику транспорта.

Исправление: отдельные серверные политики на чтение отчётов, моточасы, ремонт и заявки; объединять их с проверкой автора/профессии. Проверить каждый метод матрицей «роль × право × владелец». Не закрыть случайно общий реестр, который нужен нескольким разделам.

### S3. P1 — удаление чужих моточасов и закупок без проверки автора

Место: `src/MyApp.Application/Services/VehicleService.cs:457`; `src/MyApp.Infrastructure/Repositories/VehicleRepository.cs:886`.

`DeleteEntryAsync` проверяет пользователя только для категорий `defects` и `works`. Для `hours` и `purchases` сразу вызывается удаление по ID. Любой аккаунт с `menu.vehicles` и известным ID может удалить запись другого пользователя; ID доступны в ответе журнала.

Исправление: исчерпывающий `switch` по допустимым категориям, проверка текущего пользователя и явная политика удаления каждой сущности. Авторскую проверку желательно включить непосредственно в условие DELETE. Проверки: чужая/своя запись, администратор, неизвестная категория.

### S4. P1 — создание складского требования доступно любому вошедшему пользователю

Место: `src/MyApp.API/Controllers/ComponentDocumentController.cs:13,31`; `src/MyApp.Application/Services/ComponentDocumentService.cs:30,103`.

На генерации требования стоит только `[Authorize]`. Сервис проверяет существование пользователя, валидность документа и ответственное лицо, но не его permissions. В результате аккаунт без права работы со складом может напрямую создать документ и инициировать уменьшение остатков. Проверка фактического остатка на сервере защищает от завышенного количества, но не от неразрешённого действия.

Исправление: серверное право на выдачу материалов и доступ к `SourceTable`; согласовать использование `tables.selected_components` с бизнес-правилами. Проверять их до вызова репозитория. Отдельно определить право удаления требований: сейчас `menu.requirements` разрешает удалить любое требование и восстановить остатки (`RequirementJournalController.cs:32`), без передачи автора в сервис.

### S5. P1 — предсказуемые временные пароли и широкие права по умолчанию

Место: `src/MyApp.Application/Services/UserService.cs:67,79,377`.

Пароль строится как дата `ddMMyyyy` плюс минута `00..59`. При известной дате создания остаётся всего 60 вариантов; час в пароль не входит. Новому пользователю выдаётся весь `Permissions.All`. Срок временного пароля и обязательная смена при первом входе не реализованы в изученном потоке.

Исправление: криптографически случайный временный секрет, срок действия, обязательная смена; начальные права по принципу минимальной необходимости. DTO создания содержит UserName/Password, которые фактически заменяются генерацией: привести контракт и UI к выбранной схеме.

### S6. P1 — отсутствие защиты login от перебора

Место: `src/MyApp.API/Controllers/AuthController.cs:11`; `src/MyApp.Application/Services/AuthenticationService.cs:12`; `src/MyApp.API/Program.cs`.

В коде нет rate limiting, ограничения попыток или задержек для учётной записи. Каждый неверный пароль существующего пользователя запускает PBKDF2; это также создаёт путь к нагрузке на CPU. Для отсутствующего пользователя хеширование пропускается, что даёт временной сигнал существования аккаунта. Наличие внешнего лимитера на proxy не проверено.

Исправление: лимиты по аккаунту и источнику, ограничение параллелизма, журналирование отказов; проверка фиктивного хеша для неизвестного логина. Избегать бессрочной блокировки, которую можно использовать против владельца аккаунта.

### S7. P1 — права и пароль меняются, но выданный JWT остаётся действующим

Место: `src/MyApp.Infrastructure/Security/JwtTokenProvider.cs:19,33`; `src/MyApp.API/Extensions/JwtExtensions.cs:32`; `frontend/src/App.vue:89`; `frontend/src/components/IdleSessionWarning.vue:6`.

Роль/права помещаются в JWT на 8 часов. Валидация проверяет подпись, issuer, audience и срок, но не актуальную версию сессии. Смена пароля, снятие административной роли или logout не отзывают уже скопированный токен. Таймер бездействия очищает браузерное состояние, а не серверную сессию. Часть сервисов заново проверяет пользователя, однако административные API, полагающиеся на JWT-role, сохраняют старый доступ.

Исправление: версия сессии/security stamp с проверкой актуальности, отзыв refresh-токенов и более короткие access-токены. Смена пароля/прав должна отзывать прежние сессии. Добавить тест административного запроса со старым JWT после понижения роли.

### S8. P2 — общий встроенный хеш администратора

Место: `src/MyApp.Infrastructure/Db/DatabaseInitializer.cs:745`.

При отсутствии аккаунта с зарезервированным именем initializer создаёт администратора с фиксированным хешем из репозитория. Открытый пароль не установлен аудитом; одинаковый хеш означает одинаковый исходный пароль во всех таких установках и позволяет офлайн-подбор при доступе к исходникам. Не следует считать это подтверждённым знанием пароля боевого администратора.

Исправление: одноразовый bootstrap из защищённой конфигурации, без штатного пароля в коде; исключить повторное создание через обычный запуск API. Зафиксировать зарезервированное имя: профиль сейчас может переименовывать системного пользователя, хотя административное редактирование запрещает такую операцию.

### S9. P2 — слабая минимальная длина пароля и устаревшая стоимость PBKDF2

Место: `src/MyApp.Application/Services/UserService.cs:182,350`; `src/MyApp.Infrastructure/Security/Pbkdf2PasswordHasher.cs:10`.

Принимаются пароли от 6 символов; PBKDF2-SHA256 использует 100 000 итераций. OWASP рекомендует для этого алгоритма 600 000. Случайная соль и constant-time сравнение уже реализованы правильно.

Исправление: политика длинных паролей, проверка распространённых/скомпрометированных паролей; калибровка стоимости хеша на сервере и постепенное перехеширование при успешном входе. Увеличение стоимости сочетать с защитой login от нагрузки, а не просто менять константу.

Источник: [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).

### S10. P2 — токен в localStorage и доверие браузерной роли

Место: `frontend/src/App.vue:16,73`; `frontend/src/components/NavigationSidebar.vue:103`.

Любой исполняемый скрипт этого origin может прочитать bearer-токен. В изученном фронтенде не найдено `v-html`, `innerHTML` или `eval`; наличие localStorage само по себе не доказывает XSS. Sidebar дополнительно читает роль из localStorage и может показывать административные пункты после локальной подмены. Само по себе это не даёт права на корректно защищённый серверный endpoint.

Исправление: единое реактивное auth-состояние; при выборе cookie-сессии использовать HttpOnly/Secure/SameSite и добавить защиту от CSRF. Не переносить токен в cookie без анализа CSRF. Проверить CSP и остальные заголовки на реальном proxy; конфигурация заголовков в репозитории не установлена.

### S11. P2 — аватар и подпись доверяют Content-Type клиента

Место: `src/MyApp.API/Controllers/UserProfileController.cs:78`; `src/MyApp.API/Controllers/EmployeeSignatureController.cs:44`.

Проверяется MIME и размер, но содержимое не декодируется и не сверяется даже по сигнатуре. Content-Type задаёт клиент. Это допускает хранение произвольных байтов под видом картинки. Для фото/видео ремонта проверка сигнатур уже есть; это положительное отличие.

Исправление: ограниченное декодирование и повторное кодирование изображения, лимит размеров/пикселей, нормализация MIME. Не заявлять прямую XSS/RCE без отдельного доказательства. Для XLSX отдельно ограничить строки, ячейки и расход ресурсов: размер сжатого файла 5 МБ не ограничивает объём распаковки (`VehicleService.cs:811`), а цикл чтения не проверяет CancellationToken.

### S12. P2 — квота вложений проверяется вне атомарной операции

Место: `src/MyApp.Application/Services/VehicleService.cs:744,993`; `src/MyApp.Infrastructure/Repositories/VehicleRepository.cs:1345`.

Два параллельных upload могут оба увидеть количество ниже 10 и оба записать файлы, превысив квоту. Транзакция записи начинается после проверки count и не блокирует родителя на время проверки.

Исправление: проверять count и вставлять под одной блокировкой родительской записи/advisory lock; лимит общего объёма на пользователя/проект. Проверить конкурентные загрузки на границе квоты.

### S13. P2 — video ticket действует независимо от сессии и без лимита создания

Место: `src/MyApp.API/Controllers/VehicleController.cs:206,467,631`; `src/MyApp.API/Controllers/AuxiliaryWorkController.cs`.

Криптографически случайная ссылка позволяет анонимный stream в течение часа. Она не привязана к пользователю, не отзывается logout и права на конкретное видео при выдаче vehicle-ticket не проверяются отдельно. MemoryCache не ограничен по размеру, число tickets не ограничено. Это условный риск: временная bearer-ссылка может быть сознательным дизайном, но её свойства должны быть определены явно.

Исправление: ограничить выпуск, срок и память; проверять существование/доступ перед выдачей, связывать ticket с версией сессии, учитывать утечки ссылок через логи. Range-запросы требуют многократного использования ссылки, поэтому одноразовый ticket без поддержки видеоплеера не подойдёт. При нескольких экземплярах API локальный cache также потребует изменения.

### S14. P2 — расширенные права БД и детали ошибок

Место: `src/MyApp.Infrastructure/Repositories/CsvFileRepository.cs:19,49`; `src/MyApp.API/Controllers/CsvFileController.cs:27,61`; `src/MyApp.API/Program.cs:100`.

API использует серверное чтение/экспорт файлов PostgreSQL, а при старте выполняет DDL. Это требует более широких прав, чем обычное чтение/изменение бизнес-таблиц. Фактические GRANT и TLS подключения не установлены. Ошибки CSV возвращают клиенту `exception.MessageText`/`Message`, что может раскрывать внутренние пути и структуру БД, хотя endpoint ограничен администраторами.

Исправление: выделенная ограниченная DB-role, отдельный процесс миграций/импорта; проверить TLS и сетевые ACL. Возвращать стабильную прикладную ошибку, детали писать в серверный лог с correlation ID. Параметризованные значения и allowlist имён уже защищают изученные SQL-пути от простого SQL injection.

Источник: [PostgreSQL server-side large-object functions](https://www.postgresql.org/docs/current/lo-funcs.html).

## Целостность данных и устойчивость

### R1. P1 — транзакция БД не откатывает внешний складской CSV

Место: `src/MyApp.Infrastructure/Repositories/RequirementJournalRepository.cs:82`; `src/MyApp.Infrastructure/Repositories/CsvFileRepository.cs:49`.

Складские операции вызывают `edit_csv_tab` внутри транзакции. Если функция пишет физический CSV, успешная запись первых строк и ошибка следующих либо ошибка commit оставляют внешние остатки изменёнными при откате документа в БД. Сам код отмечает это ограничение. Предварительные проверки всех позиций и advisory lock уменьшают вероятность ошибки, но не обеспечивают атомарность. `lo_export` тоже пишет файл вне откатываемых строк БД.

Исправление: хранить авторитетные остатки в PostgreSQL, экспортировать CSV после commit через устойчивую очередь/outbox; обеспечить повторяемость и сверку. Если CSV должен остаться авторитетным, разработать журнал операций и восстановление с атомарной заменой файла. Интеграционные тесты текущего репозитория используют DB-stub, а не реальные физические записи; они не доказывают атомарность с CSV.

### R2. P1 — бесконечные повторы фонового переноса файлов

Место: `src/MyApp.API/BackgroundServices/StagedMediaTransferService.cs:46,64,74`; `src/MyApp.Infrastructure/Repositories/MediaStorageAdministrationRepository.cs:42`.

При полном пакете из 100 записей цикл немедленно читает следующий пакет. Ошибка переноса только логируется, запись остаётся кандидатом. Если 100 самых старых файлов постоянно не переносятся, сервис бесконечно выбирает их, нагружает БД/диск/логи и не доходит до остальных. Причиной могут быть отсутствие исходника, неверный Size или права каталога.

Исправление: retry/backoff, ограничение попыток/времени на проход, nextAttemptAt/статус ошибки, выход при отсутствии прогресса. При нескольких API-репликах добавить claim/lease: текущие копирование, `File.Move(...overwrite:true)` и условное обновление пути не обеспечивают эксклюзивное владение переносом.

### R3. P2 — принятие ремонта без проверки профессии/детального права

Место: `src/MyApp.Application/Services/VehicleService.cs:211`; `src/MyApp.Infrastructure/Repositories/VehicleRepository.cs:369`.

Назначение проверяет существование и отсутствие исполнителя, но не разрешённую профессию. При этом завершение ремонта имеет дополнительные ограничения. Пользователь с общим доступом может назначить себе задачу, которую затем не сможет завершить, и заблокировать принятие другим работником.

Исправление: одинаковая политика допустимого исполнителя на claim и complete; сохранить атомарное условие назначения, которое уже препятствует двойному claim.

## Производительность и качество фронтенда

### F1. P2 — загрузка всего реестра при показе восьми строк

Место: `frontend/src/components/HomeView.vue:55,75,142`; `src/MyApp.API/Controllers/VehicleController.cs:29`.

Пагинация и поиск полностью клиентские. На каждом mount загружается весь реестр, поиск перебирает шесть полей каждой машины и заново приводит их к нижнему регистру. computed кеширует результат до изменения зависимостей, поэтому проблема зависит от размера парка; для небольшого парка это допустимо.

Исправление: при росте данных — API поиска/пагинации и отдельная сводка показателей. При сохранении клиентской модели — заранее вычислять поисковую строку на машину, возвратить полный массив без `.filter` при пустом запросе. Кешировать реестр и инвалидировать после мутаций; не вводить виртуализацию восьми видимых строк.

### F2. P2 — гонки запросов и неправильная регистрация очистки в TablesView

Место: `frontend/src/components/TablesView.vue:381,416,433,448`.

Запросы таблицы не отменяются и не имеют sequence guard. Старый медленный ответ может перезаписать результаты более свежего поиска/выбранной таблицы. `onBeforeUnmount(clearSignatureUrls)` вызывается внутри async `loadTable` после `await`, когда нет активного контекста setup. Очистка не регистрируется надёжно; searchTimer также не очищается при unmount.

Исправление: AbortController плюс проверка актуальности запроса, cleanup на верхнем уровне setup; в cleanup отменить таймеры/запросы и освободить blob URL. Только актуальный запрос должен менять loading/error/rows. Аналогично в `HomeView.vue:167` старый отменённый запрос может сбросить loading для нового запроса через свой finally.

### F3. P2 — множество запросов подписей и дублирование аватара

Место: `frontend/src/components/TablesView.vue:153,404`; `frontend/src/components/NavigationSidebar.vue:129`; `frontend/src/components/UserAvatar.vue:26`.

Для каждой строки с подписью выполняется отдельный HTTP-запрос, все запускаются сразу через Promise.all. При `pageSize=all` их число не ограничено. Аватар запрашивается sidebar и компонентом в заголовке страницы; при переключении страниц повторяется загрузка.

Исправление: подгружать подписи только при показе/просмотре, ограничить параллелизм и кешировать; использовать общую загрузку профиля/аватара с инвалидированием при изменении. Добавить отмену/guard и обработку сетевых ошибок в loadProfile/loadAvatar, чтобы поздний ответ после unmount не создавал забытый blob URL.

### F4. P3 — все страницы импортируются заранее

Место: `frontend/src/App.vue:2`.

Основной JS после сборки: 313,35 кБ, gzip 92,89 кБ; CSS: 97,95 кБ, gzip 17,54 кБ. Страницы с таблицами, ремонтами и настройками импортируются статически даже для экрана входа. PDF-библиотеки уже используют динамический import; chunk fontkit 710,92 кБ не означает, что он скачивается при первом открытии.

Исправление: defineAsyncComponent для крупных страниц/диалогов, проверить Network на входе и первом открытии каждой страницы. Оптимизировать логотип 459,41 кБ под реальный отображаемый размер. Шрифты PDF не заменять на WOFF без проверки поддержки PDF-инструментов.

### F5. P3 — глобальная подмена fetch связывает любые 401 с logout

Место: `frontend/src/main.js:10`.

Обёртка реагирует на любой 401 при наличии localStorage-токена, не проверяя origin/API и принадлежность запроса текущей сессии. Запоздалый ответ от предыдущей сессии также может выйти из новой.

Исправление: явный API-клиент с проверкой пути/origin и поколения сессии, единая обработка ошибок. Нормализовать работу с Request/URL; текущая обёртка в основном рассчитана на строковые пути.

## Производительность бэкенда и БД

### B1. P2 — таблицы сериализуются в JSON для поиска и сортировки

Место: `src/MyApp.Infrastructure/Repositories/TableViewRepository.cs:30,65,88`.

`row_to_json(t)::text ILIKE '%...%'` требует обработки всех полей, обычные B-tree индексы не обслуживают такой поиск. `ORDER BY row_to_json(t)::text` добавляет сортировку по вычисленной строке всей записи. COUNT и выборка выполняют отдельные запросы. При `pageSize=all` полностью материализуется результат; пользователь с доступом к таблице может инициировать большой ответ и большой DOM. `(Page - 1) * limit` также может переполнить int при произвольном page.

Исправление: стабильная сортировка по явным колонкам и ключу; поиск по нужным полям, при необходимости trigram/full-text и отдельная локальная таблица вместо дорогого foreign view. Запретить неограниченную выдачу в обычном endpoint, экспортировать отдельно; ограничить page/search и считать offset безопасно. Возможность индексации зависит от устройства представлений/foreign tables, которое не установлено.

### B2. P2 — repair-journal возвращает всю историю для всего парка

Место: `src/MyApp.Infrastructure/Repositories/VehicleRepository.cs:217`; `frontend/src/components/VehicleHours.vue:12`; `frontend/src/components/ShiftReport.vue:34`.

Запросы уже сгруппированы, что лучше N+1 на каждую машину, но число строк не ограничено: загружаются все дефекты, работы, участники и метаданные вложений. Моточасы используют этот большой endpoint, хотя им нужна техника и последние показания. Отчёт загружает также архив и затем фильтрует на клиенте.

Исправление: отдельная сводка моточасов; выборка отчёта по дате/смене; пагинация истории, компактная сводка парка и детали по запросу. Последнюю завершённую работу на дефект выбирать в SQL: сейчас `VehicleRepository.cs:999` загружает все завершённые работы и берёт первую после группировки в памяти.

### B3. P2 — импорт моточасов имеет сложность строки × весь парк

Место: `src/MyApp.Application/Services/VehicleService.cs:329`.

Каждая импортируемая строка сканирует весь массив машин через Where/ToArray. При R строках и V машинах это O(R×V).

Исправление: lookup по `(гаражный номер, нормализованная модель)` с сохранением проверки неоднозначности; O(V+R). Ограничить число строк/ошибок, использовать потоковый CSV и контроль отмены. В AddHours для второго ДВС (`:299`) и SaveEngine в GtoSettingsController (`:43`) заменить чтение всего парка на точечный запрос одной машины.

### B4. P2 — лишняя память при upload и несогласованные лимиты видео

Место: `src/MyApp.API/Controllers/VehicleController.cs:174,431`; `src/MyApp.Infrastructure/Repositories/VehicleRepository.cs:1554`.

Видео копируется в MemoryStream, затем ToArray создаёт ещё одну копию; в момент обработки большого файла память превышает его размер более чем вдвое без учёта multipart-буферизации. Фотографии с диска читаются целиком в byte[]. Видео скачиваются потоком и с range — это уже реализовано правильно.

Контроллер транспорта обещает 100 МБ, но не задаёт RequestSizeLimit для этих upload. Стандартный лимит Kestrel — 30 000 000 байт, если он не переопределён хостингом. В AuxiliaryWorkController необходимые атрибуты уже есть. В штатной конфигурации крупный vehicle-upload будет отклонён раньше проверки 100 МБ.

Исправление: потоковый upload во временный файл с проверкой размеров/заголовка и атомарной фиксацией; согласовать request/form/proxy лимиты. Для фото — stream, thumbnails, cache validators и квоты параллелизма.

Источник: [Microsoft: ограничения загрузки файлов](https://github.com/dotnet/AspNetCore.Docs/blob/main/aspnetcore/mvc/models/file-uploads.md).

### B5. P2 — широкое чтение пользователей включает бинарные аватары

Место: `src/MyApp.Infrastructure/Repositories/UserRepository.cs:10,20,31`.

Login, списки и авторизационные проверки загружают полную сущность User, включая AvatarContent, хотя обычно нужны несколько полей. Аватар допускает 2 МБ, поэтому большие списки пользователей могут переносить значительный объём из БД без использования. ToProfile и GetAll DTO строятся после материализации сущностей.

Исправление: проекции для login/прав/профиля/списка; бинарное содержимое получать отдельным запросом. Для read-only запросов применять AsNoTracking, сохраняя tracking для обновлений. `ToLower()` в проверке уникальности логина требует согласованного индекса по LOWER или citext; текущий уникальный индекс case-sensitive, а прикладная проверка case-insensitive и подвержена конкурентной гонке.

### B6. P3 — функции даты и многочисленные round trips

Место: `src/MyApp.Infrastructure/Repositories/VehicleRepository.cs:1294`; `src/MyApp.API/Controllers/GtoSettingsController.cs:19,78`; `src/MyApp.Infrastructure/Repositories/RequirementJournalRepository.cs:36`.

Фильтры используют `CreatedAt.Date`, что затрудняет использование обычного индекса по времени. Проверка CanEdit получает все каталоги, хотя нужен только факт разрешения. Настройки дефектов и складские позиции обрабатываются последовательными SQL-запросами.

Исправление: сравнивать сам CreatedAt с `[начало, следующий день)` в согласованном часовом поясе; отдельный метод проверки прав, bulk-upsert и групповое чтение остатков под существующей блокировкой. Не запускать параллельно запросы на одном DbContext: он не предназначен для этого. Подтвердить изменения через EXPLAIN (ANALYZE, BUFFERS) на тестовых данных; не добавлять индексы вслепую.
