# Локальный помощник Atlas: прототип и ограничения

## Аудит PostgreSQL, 26.10.2026 (Asia/Sakhalin)

Проверка выполнена инструментом `MyApp.LocalAdvice.Evaluation --audit` через существующее
подключение DefaultConnection. Транзакция REPEATABLE READ + READ ONLY. Инициализатор API
и миграции не запускались, рабочие тексты и персональные данные не выгружались.
Первоначальные попытки соединения завершались тайм-аутом; повторная проверка старого
подключения прошла. Адрес, предложенный отдельно пользователем, также давал тайм-аут.

| Показатель | Значение |
| --- | ---: |
| Машины | 40 |
| Неисправности | 22 |
| Глубина истории неисправностей, полных дней | 6 |
| Неисправности с заполненным узлом | 0 |
| Неисправности с симптомами | 22 |
| Причина отказа дословно совпадает с симптомами | 20 |
| Завершённые ремонты | 1 |
| Завершённые ремонты с датой завершения | 1 |
| Показания моточасов | 486 |
| Неисправности с будущим created_at | 0 |
| Таблица подтверждённых фактов смены | отсутствует |

Старый `VehicleRepository.AddDefectAsync` записывал пустой узел и копировал симптомы
в причину отказа. Новый код сохраняет эти поля отдельно, только после отправки формы
пользователем. Старые записи не переписываются. Дополнительно в старом миграционном коде
узел мог заполняться из description/part_article; такие значения нельзя автоматически
считать нормализованным справочником узлов.

## Решение о технологии

Обучаемая модель и локальная LLM пока **не подключены**. Из шести дней истории, одного
ремонта, отсутствующих узлов и фактов смен нельзя получить надёжную временную проверку.
Глубина истории меньше выбранного 30-дневного горизонта повторения. 486 показаний
моточасов не заменяют целевые метки. Размеры и характеристики оборудования для LLM
не проверены; установка весов сейчас не обоснована данными.

Реализован детерминированный локальный прототип внутри ASP.NET Core: `local-rules-v1`
и `local-extract-v1`. Нет внешних ИИ-вызовов, новых ML-пакетов, отправки текстов,
телеметрии модели или журналирования тела заявки. Это **не обученный ИИ-прогноз**.

## Семантика

Готовность: фактическая техническая возможность работать **всю смену**, независимо от
организационного простоя. Ручной forecast в ГТО не является фактом. Прототип читает
текущие неисправности, ремонты и наличие показаний часов, объясняет необходимость
проверки и всегда возвращает `insufficient_data`, `confidence: null`. Отсутствие
неисправностей не трактуется как подтверждённая готовность. Дата/смена обязательны;
разрешены сегодня и следующие семь дней. Исторические прогнозы по текущей редактируемой
истории запрещены. Время начала смены не установлено — расчёта вероятности успеть к нему нет.

Повтор: **другой ID неисправности той же машины и того же узла**, возникший после
зарегистрированного завершения ремонта предыдущей неисправности и не позднее 30 дней
после него. Граница 30 дней включается; одновременные события не считаются повтором.
Узел сравнивается после trim, нормализации пробелов, регистра и ё/е. Это консервативное
определение требует последующего согласования отраслевого справочника узлов.
Обновления одного ID и несколько работ по нему не увеличивают число неисправностей.
Показанное совпадение — исторический сигнал для проверки, **не вероятность будущей поломки**.
При пустом узле или отсутствии подтверждённой модели риск не оценивается числом.

Разбор: распознаются явно подписанные поля через `:` с разделителями `;` или новой строкой.
Ремонт: Узел, Симптомы/Описание, Причина, Код ошибки. Закупка: Описание, Запчасти.
Свободный текст предлагается целиком как симптомы/описание; причины не выдумываются.
Противоречащие значения одного поля пропускаются. Каждое значение можно изменить,
принять флажком или отклонить. Запчасти переносятся в существующее описание закупки.
«Перенести выбранное» меняет только форму, сохранение выполняется существующей кнопкой.

## API и хранение

Все методы требуют существующую политику `menu.vehicles` и соответствующее право:

| Метод | Дополнительное право | Запись |
| --- | --- | --- |
| GET `/api/local-advice/vehicles/{id}/readiness?date=YYYY-MM-DD&shift=1` | reports.gto / legacy vehicles.report | нет |
| GET `/api/local-advice/defects/{id}/recurrence` | vehicles.repair / vehicles.repair_history / legacy vehicles.works | нет |
| POST `/api/local-advice/parse` `{kind:repair\|parts,text}` | vehicles.repair_request / vehicles.parts_request | нет |
| GET `/api/local-advice/quality` | reports.gto / legacy vehicles.report | нет |
| POST `/api/local-advice/vehicles/{id}/outcomes` | отчёт + существующий CanManage механика | только явно подтверждённый факт |

Факт: `{date,shift,readyWholeShift,confirmed:true}`. Только даты раньше сегодняшней
в Asia/Sakhalin, смены 1/2, явно выбранное булево значение. Новая таблица
`vehicle_shift_outcomes` создаётся штатным DatabaseInitializer. Повторный факт по тому же
ключу даёт 409; автоматической перезаписи нет. Исправление ошибочного факта пока требует
отдельного административного процесса с аудитом. Факт не меняет ГТО и состояние техники.
Форма подтверждения доступна в историческом ГТО механика, если сохранён отчёт за дату.

Ответы рекомендаций содержат `generatedAt`, `expiresAt` (5 минут), версию и объяснения.
HTTP `no-store`; клиент не сохраняет рекомендации в localStorage. Ошибка/тайм-аут API,
offline, смена пользователя/машины/смены и обновление журнала очищают результат.
Состояние БД могло измениться после чтения — UI явно требует обновления после изменений.
Нет фоновой подписки на изменения с других клиентов. После истечения срока результат удаляется.

Android содержит ТО и базовый раздел ремонта, но не формы ГТО/закупки. Его DTO, офлайн-очередь
и локальная БД не содержат рекомендаций; старый ответ ИИ как актуальный он не показывает.
Новые экраны помощника на Android не реализованы. При их добавлении нужен отдельный
online-only запрос с тем же сроком действия; не включать ответы в MaintenanceSnapshot.

## Отчёт о качестве

На реальных данных временная валидация **невозможна**: нет надёжных целевых меток
и снимков признаков на момент прогноза. Готовность: accuracy/recall/Brier/калибровка —
не определены. Риск: precision/recall/Brier — не определены, горизонт не наблюдён.
Числовые прогнозы отключены, покрытие числовыми прогнозами — 0% по конструкции.
Размеченной реальной выборки извлечения полей нет, её реальные precision/recall/F1
также не определены. Результаты синтетических тестов не доказывают производственную точность.

`synthetic-extraction.json` — только придуманные примеры без рабочих данных. Для проверки
механизма временной валидации cutoff = 2026-10-01T00:00:00Z: 1 ранний пример, 5 отложенных.
Отдельный пример свободного текста демонстрирует ограничение правил. Отчёт создаётся
командой ниже. На этих пяти **синтетических** примерах: precision 0,80; recall 0,667;
F1 0,727; exact match 0,80; покрытие непустыми черновиками 0,60. Это проверка инструмента,
не оценка точности на истории Atlas. Ранние примеры не участвуют в метриках; одинаковые ID и снимки, созданные
позже времени исходного события, исключаются. Версия извлекателя фиксирована, обучение
на holdout отсутствует. Метрики считаются по точным парам имя/значение, micro precision,
recall, F1, доля полностью верных заявок и покрытие непустыми черновиками.

Нужно начать собирать: факты смен с автором/временем; неизменяемые снимки входных признаков
до смены; единый узел и отдельную установленную причину; время появления/закрытия дефекта;
полные 30 дней последующего наблюдения после ремонта; проверенные поля заявок и решения
механика принять/исправить/отклонить. Автоматическое накопление снимков признаков и
разметки правок ещё не реализовано. Текущие редактируемые записи нельзя использовать
для восстановления point-in-time признаков без дополнительного аудита.

Для следующей версии: обучать на ранних периодах, настраивать на следующем периоде,
финально проверять на более позднем, исключить утечку через поздние правки и незавершённые
30-дневные окна. Согласовать цену пропуска неготовой машины; сравнить с простым baseline;
оценить recall неготовности, false-ready, Brier, калибровку и покрытие отказами. Для риска
считать метрики по независимым дефектам, для текста — по каждому полю. До этой проверки
прототип не повышает уверенность автоматически при росте числа записей.

## Воспроизведение

```powershell
dotnet build src/MyApp.API.sln
dotnet test src/MyApp.API.sln --filter 'Category!=Integration'
dotnet run --project src/MyApp.LocalAdvice.Evaluation -- --audit src/MyApp.API/appsettings.json
dotnet run --project src/MyApp.LocalAdvice.Evaluation -- --evaluate docs/local-advice/synthetic-extraction.json 2026-10-01T00:00:00Z
cd frontend
npm run build
npx playwright test tests/local-advice.spec.js
```

Аудит использует .NET User Secrets существующего API; не передавать пароль аргументом.
Необязательный третий аргумент после `--audit` и пути конфигурации переопределяет только
host для явно разрешённой проверки. Аудит печатает агрегаты, ошибки — только тип/SQLSTATE.
Команда evaluate читает локальную размеченную JSON-выборку; не выводит исходные тексты.

Проверено: сборка .NET без предупреждений, 161 серверный модульный тест; сборка Vue;
26 браузерных сценариев ГТО/ремонта/закупок, включая 7 новых сценариев на синтетическом API;
сборка Android debug и 9 unit-тестов.
В сборке Vue остаётся предупреждение о крупных чанках, в Android — предупреждения SDK/
Kotlin окружения, сборка завершилась успешно. Полный PostgreSQL integration suite
требует отдельной одноразовой БД `*_test` и в этой сессии не запускался на рабочей БД.
Изменения не развёрнуты на сервере.
