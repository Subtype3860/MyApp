# Отчёт за смену

В разделе «Транспорт → Отчёт» доступны предпросмотр и скачивание PDF из записей истории ремонта и вспомогательных работ. Пример оформления на демонстрационных данных: `examples/shift-report-preview.pdf`. Ссылки в примере указывают на локальный тестовый сервер; реальные отчёты используют адрес приложения, на котором их сформировали.

Дата при открытии раздела вычисляется по местному времени браузера: до 12:00 — предыдущий день, с 12:00 — текущий день. Дату и смену можно изменить для повторной выгрузки. По умолчанию до полудня выбрана смена 2, после — смена 1. В базе отдельные дата по графику, номер смены и интервал не добавляются.

Отбор использует уже существующее время работы `completedAt`, а при его отсутствии — `createdAt`. Первая смена: [08:00, 20:00), вторая: [20:00, 08:00 следующего дня). Время переводится в местный часовой пояс браузера. На рабочих устройствах должен быть установлен часовой пояс участка.

Группировка: КАРЬЕР / РММ → тип техники → машина; внутри каждого места после ремонта выводится блок «Вспомогательные работы». Работы внутри машины перечисляются по времени. Состояние определяется по известным дефектам и работам до окончания выбранной смены, а не по сегодняшнему состоянию карточки. Если данных о состоянии недостаточно, выводится «Состояние не указано».

В новые записи ремонта добавлено поле `location` со значениями КАРЬЕР / РММ. Колонку `vehicle_works.location` создаёт существующий DatabaseInitializer при запуске API. Старые записи остаются без места: пользователь выбирает его для текущего отчёта перед выгрузкой; выбор старых записей в базу не записывается. Для новых работ место обязательно в форме; API принимает пустое значение для совместимости со старыми клиентами.

PDF содержит до двух уменьшенных фотографий на блок машины (JPEG, максимум 720 пикселей по большей стороне), ссылки на оригиналы и все видео. Недоступное превью не препятствует выгрузке; ссылка на материал сохраняется. Видео не встраивается и не скачивается при формировании.

Ссылки ведут в приложение с идентификаторами работ и медиа. После обычного входа открывается существующий просмотрщик, использующий защищённые API фотографий и краткосрочные stream-ticket для видео. В PDF не попадают токены и временные ссылки на поток. Доступность оригиналов зависит от сохранности работ и вложений в истории ремонта.

Это первый вариант фактического отчёта за смену с ремонтом и вспомогательными работами. Прогноз «Выход ГТО», архив неизменяемых отчётов, публикация и автоматическая отправка в этом изменении не реализованы.

## Исполнители и подтверждение участия

Для каждой работы в предпросмотре и PDF выводятся ФИО и должности подтверждённых исполнителей. Заявки `pending` и `rejected` не включаются в список исполнителей отчёта. Если подтверждённых исполнителей нет, это явно указано.

В «Ремонте» и «Истории ремонта» сотрудник может нажать «Я участвовал в работе». Пользователь берётся из авторизованной сессии; выбрать другого сотрудника этим запросом нельзя. Механик подтверждает или отклоняет участие в блоке исполнителей соответствующего этапа. После отклонения можно подать заявку повторно. Подтверждение не даёт права редактировать или удалять чужую работу и медиа.

Сервер проверяет профессию «Механик» по данным пользователя в базе. Роль administrator сама по себе права подтверждения не даёт. Решение хранится с идентификатором механика и временем рассмотрения. При повторной подаче отклонённой заявки прежние поля решения сбрасываются; хранится текущее состояние, отдельный журнал всех решений не ведётся.

Таблица `vehicle_work_participants` создаётся DatabaseInitializer. Пара `(work_id, user_id)` уникальна. Автор новой работы получает заявку `pending` в той же транзакции, что и запись работы. Ранее зарегистрированные исполнители переносятся как сохранённые прежние сведения, без фиктивного механика и даты подтверждения. В интерфейсе такие записи помечаются «Ранее указанный исполнитель».

API:

- `GET /api/vehicles/works/{workId}/participants` — список участников;
- `POST /api/vehicles/works/{workId}/participants` — заявить своё участие, без тела запроса;
- `POST /api/vehicles/works/{workId}/participants/{participantId}/review` с `{ "approved": true/false }` — решение механика.

Повторное заявление при статусе pending/approved возвращает конфликт. Рассмотрение меняет только pending-заявку указанной работы, поэтому одновременные решения не перезаписывают друг друга. Для применения таблицы требуется обновить и перезапустить API. Проверены серверные права, интерфейс и PDF; миграция на рабочей базе в рамках этой задачи не запускалась.


## Вспомогательные работы

В основном меню добавлен отдельный пункт «Вспомогательные работы». Его можно предоставить сотруднику без доступа к транспорту через право `menu.auxiliary_works` в существующих настройках пользователей. Администратор получает это право в новом токене при входе.

Сотрудник указывает название, место КАРЬЕР/РММ, дату и время, описание результата и прикладывает фото/видео. В форме нет выбора техники. Можно приложить до 10 фото и 10 видео; используются существующие ограничения и проверка содержимого (JPEG/PNG/WebP и MP4/WebM/MOV). Автор записи заявлен как исполнитель со статусом pending; другие сотрудники могут заявить своё участие. Механик подтверждает участников так же, как при ремонте.

Записи хранятся в существующем журнале работ с `work_kind = auxiliary` и без `vehicle_id`/`defect_id`. Для этого DatabaseInitializer добавляет `work_kind` и `title`, делает ссылку на машину необязательной и вводит проверку: ремонт имеет машину, вспомогательная работа не имеет ни машины, ни дефекта. Медиавложения и участие используют общий механизм хранения; перенос и администрирование файлов продолжают учитывать эти записи. Журналы техники отбирают только работы, связанные с машиной.

`GET /api/auxiliary-works` разрешён сотрудникам с доступом к этому меню либо к отчёту транспорта. Создание, загрузка вложений и действия с участниками требуют отдельного права вспомогательных работ. API проверяет принадлежность работы и медиа к вспомогательным работам, чтобы доступ к этому меню не давал доступа к файлам ремонта транспорта. Загружать вложения может автор вспомогательной записи независимо от профессии; проверки подтверждения механиком сохраняются на сервере.

Отчёт загружает оба источника. Если один недоступен, выгрузка блокируется, чтобы не создать неполный документ. Дата и смена отбираются по тем же границам 08:00/20:00. Вспомогательные работы не получают статус машины и не входят в подсчёт техники. Подтверждённые исполнители, фото-превью и ссылки на видео выводятся в общем PDF. Ссылки на такие материалы открывают отдельный раздел с авторизацией.

При ошибке загрузки вложения форма сохраняет ID уже созданной записи и повторяет только оставшиеся загрузки, не создавая работу заново. В случае ухода со страницы исходные выбранные файлы не сохраняются локально.

Проверены интерфейс на телефоне/десктопе, создание записей, медиа, повтор загрузки, подтверждение механиком, автономные права меню, ночные смены, общий PDF и перенос длинного текста между страницами. Изменения базы подготовлены в DatabaseInitializer; на рабочей базе в этой задаче не применялись.
