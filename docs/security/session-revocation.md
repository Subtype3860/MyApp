# Отзыв JWT и доступ к моточасам

Изменять показания, импортировать CSV/XLSX, удалять записи моточасов и сохранять показания/моточасы замены ДВС могут:

- администратор;
- механик или старший механик;
- пользователь с явно назначенным правом `vehicles.hours`.

Решение принимает сервер по актуальному пользователю из БД. Право просмотра меню транспорта или отчётов само по себе не разрешает изменение моточасов. Механикам право моточасов добавляется в эффективные permissions при входе; дополнительные права других разделов автоматически не выдаются. API fleet-options возвращает `canManageHours` для состояния элементов интерфейса.

Для складского требования действует отдельное правило: подготовка и создание через `/api/documents/components/preview` и `/api/documents/components` доступны только профессии «Механик» (регистр и пробелы нормализуются). Роль администратора и назначенные permissions не обходят это условие; «Старший механик» также не включён. Профессия читается из БД перед обработкой документа и изменением остатков. Остальные профессии получают 403 с понятным сообщением.

Каждый новый JWT содержит случайную `session_stamp`, сохранённую в `app_users.session_stamp`. После обычной проверки подписи и срока bearer middleware сверяет ID и stamp с БД без кеширования. Отсутствующий пользователь, несовпадающая версия или старый токен без stamp получают 401. Уже выполняющийся запрос не отменяется задним числом.

Версия меняется при изменении пароля, логина, роли, назначенных прав или профессии пользователя. Изменение ФИО/аватара не отзывает сессии. `POST /api/auth/logout` меняет версию для всех сессий пользователя; выход на одном устройстве завершает доступ на остальных. Обработчик logout обновляет только совпадающую версию: запоздалый запрос со старым stamp не перезаписывает новую версию. Выход по таймеру бездействия вызывает тот же endpoint. Если запрос выхода не удаётся из-за сети/ошибки сервера, интерфейс сообщает об ошибке и позволяет повторить выход.

Временные ссылки на видео также привязаны к ID и stamp выдавшей их сессии и проверяются перед каждым новым запросом. После отзыва новая загрузка по старой ссылке получает 401. Уже переданные браузеру байты и открытый поток не возвращаются и не отменяются задним числом.

При выпуске новой версии initializer автоматически добавляет столбец; для управляемого развёртывания есть `scripts/migrations/20261012_user_session_stamp.sql`. Все JWT, выданные предыдущей версией приложения, будут отклонены, поэтому пользователям потребуется повторный вход. Если развёртывание выполняется на нескольких репликах, обновить все экземпляры: старый сервер ещё не проверяет stamp.

Проверка stamp добавляет один короткий запрос по первичному ключу пользователя на каждый авторизованный HTTP-запрос. Прямые изменения данных через SQL в обход UserService должны также менять `session_stamp = gen_random_uuid()`, если требуется отзыв ранее выданных токенов.
