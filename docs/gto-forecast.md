# Выход ГТО: прогноз, автосохранение и история

Раздел «Отчёты → Выход ГТО» формирует прогноз готовности всего активного парка, сгруппированного по справочнику group_car (поле vehicle.groupName в API). Дату и смену выбирает механик. По умолчанию предлагается следующая смена относительно существующего правила приложения: до 12:00 исходная дата — предыдущий день и исходная смена — 2, после — текущий день и смена — 1. После исходной смены 2 предлагается смена 1 следующего дня; после смены 1 — смена 2 той же даты.

Данные текущего ремонта берутся из `/api/vehicles/repair-journal`: состояние техники, нерешённые неисправности и даты начала простоя. Завершённые работы со статусом repaired закрывают соответствующую неисправность. API также возвращает в hours последнее зарегистрированное показание моточасов каждой машины (дата, значение и примечание), а не всю историю показаний. Архивная техника в прогноз не включается.

В форме показана активная остановленная техника, а также техника с открытой заявкой на ремонт или закупку ЗЧ независимо от состояния эксплуатации. Для неё механик выбирает состояние к смене: «Исправен» или «Неисправен». По умолчанию оно соответствует текущему состоянию. В PDF сохраняется весь активный парк: для техники вне формы состояние подставляется из ремонта, без применения старых черновиков. В колонке «Исправно / Неисправно» только operationalState = stopped означает «Неисправен», все остальные состояния — «Исправен». Ручной прогноз не переопределяет эту колонку; итог готовности использует то же правило. В итог выхода включается состояние «Исправен». Прежние значения черновика автоматически преобразуются в два состояния. Примечание механика, плановый выход (дата/смена либо условие), КТГ, вид ТО и состояние кондиционирования/отопления — необязательные поля. КТГ вводится вручную в диапазоне 0–100%; расчёт КТГ из истории не добавлен.

Форма доступна для редактирования механикам, старшим механикам и администраторам по признаку canManage существующего API. Остальные пользователи с правом просмотра раздела могут открыть и экспортировать сохранённые отчёты. Прогноз не изменяет ремонты и не создаёт работ.

PDF в альбомной ориентации содержит поля исходного образца, дополнительную колонку прогноза, итоги по группам и общую сводку выхода. Поиск техники в форме не меняет состав PDF: экспортируется весь парк. Длинные тексты переносятся на новые страницы.

Полный отчёт автоматически сохраняется в PostgreSQL после изменения с задержкой 500 мс. Ключ общего отчёта — дата и смена; все пользователи с доступом к разделу читают один снимок. Сохраняются поля шапки, техника и её наименования, состояние, моточасы, ремонтные и закупочные примечания, КТГ, вид ТО, планы выхода и данные климатических установок. PDF, Excel и PNG строятся из открытого снимка.

В «Неисправность/примечание» включаются все незакрытые заявки на закупку запчастей соответствующей машины (CompletedDate = NULL), с номером, датой, описанием и требуемыми запчастями. API возвращает их в partsRequests на уровне журнала, поэтому заявки без ремонтных работ также учитываются. Дубли в работах исключаются по идентификатору. Закрытые заявки не выводятся.

Оформление примечаний: «ОЗЧ Требуется: описание выполненных работ — (тело заявки на закупку)». ОЗЧ означает «отсутствие запасных частей» и выводится только при последнем статусе ремонта «Ожидает запчасти», даже без заявки на закупку. Текст ремонтной заявки выделяется жирным. Несколько закупочных заявок для одной неисправности выводятся отдельными скобками после одного текста ремонта; неисправности без закупок остаются отдельными строками. Номер добавляется только если он не повторяет начало тела заявки. «Неисправен» выделяется красным и жирным.

В разделе «Заявка на закупку ЗЧ» колонка называется «Требуется». В ГТО используется то же description последней работы по defectId независимо от статуса; если работ нет, берётся symptoms соответствующей неисправности. Дополнительно выводится requiredParts закупочной заявки без повторяющихся фрагментов.

Текст закупочной заявки, «Требуется» и дата выводятся внутри скобок в указанном порядке, без пустых разделителей; требуемое выделяется курсивом. Открытые закупочные заявки вместе с «Требуется» сохраняются и при прогнозе «Исправен». Формат общий для формы, PDF, Excel и PNG. При нехватке ширины текст переносится внутри ячейки.

Компоновка PDF уплотнена. Перед выводом сводки измеряется высота всего блока, включая переносы названий групп: при нехватке места он переносится целиком на новую страницу без шапки таблицы. Обычные строки таблицы удерживаются вместе; слишком длинные строки допускают продолжение. Для размещения всего парка на одном листе автоматически выбирается альбомный либо книжный A4. Если объём примечаний превышает вместимость одного листа, сохраняется многостраничный отчёт со сводкой без разрыва. Проверочный отчёт с 39 машинами размещается на одном A4.

## Постоянные настройки

Организация и участок сохраняются в `gto_user_settings` для текущего авторизованного пользователя. Состояние кондиционирования/отопления сохраняется в `gto_vehicle_settings` по ID техники. Плановый выход хранится в `gto_defect_settings` по ID открытой ремонтной заявки; для поля машины он сохраняется за текущими открытыми заявками этой машины. После закрытия соответствующей заявки значение перестаёт использоваться и не переносится на новый ремонт. Поля сохраняются автоматически при изменении (для текста — при выходе из поля). API проверяет права механика/старшего механика/администратора и принадлежность ремонтных заявок технике, отклоняя устаревший состав заявок.

`GET /api/gto-settings` возвращает собственные пользовательские настройки и технические настройки. `PUT /api/gto-settings/user` изменяет только настройки текущего пользователя. `PUT /api/gto-settings/vehicles/{id}` сохраняет климат и плановый выход с проверкой списка открытых defectIds. Таблицы создаются DatabaseInitializer. Существующие настройки из локального черновика переносятся в базу один раз при первом открытии новой формы, если серверных значений ещё нет.

При создании нового отчёта КТГ и вид ТО переносятся по ID техники из ближайшего предыдущего сохранённого отчёта. Прогноз и примечания новой смены формируются заново. Старый браузерный черновик используется только для первого текущего отчёта при отсутствии предыдущего серверного снимка. Резервная копия несохранённых правок хранится отдельно по пользователю, дате и смене; она автоматически восстанавливается только при совпадении серверной версии.

Сводка из формы удалена, поиск перенесён в верхний блок. Без поискового запроса показывается остановленная техника и техника с открытыми заявками на ремонт или закупку ЗЧ, при поиске — любая подходящая техника активного парка независимо от состояния. PDF всегда содержит весь парк. Заявки на ремонт и закупку ЗЧ отображаются независимо от исправности и ручного прогноза. Для неостановленной техники в документе скрываются начало простоя и плановый выход; сохранённые планы и история ремонта не изменяются. Примечание механика выводится непосредственно после текста заявки, перед курсивной причиной ожидания запчастей.

Порядок групп в форме, PDF и сводке определяется полем `group_car.report_sort_order` (integer NOT NULL DEFAULT 0) по возрастанию. Меньшее число означает более раннюю позицию. При равенстве группы упорядочиваются по имени. API передаёт значение как `vehicle.groupReportSortOrder`. Поле добавляется DatabaseInitializer и отдельной миграцией `scripts/migrations/20261012_group_report_sort_order.sql`. Существующие и новые группы по умолчанию имеют значение 0.

## Показания каждого двигателя

Самосвалы (включая «Карьерный самосвал» и «Автосамосвал») имеют два ДВС, остальная техника — один. API передаёт `vehicle.engineCount`. В форме для каждого ДВС вводятся дата показаний, текущая наработка и моточасы машины при замене этого ДВС. Изменения сохраняются при выходе из поля; ввод наработки создаёт историческую запись.

`vehicle_hour_readings.engine_number`: 1 или 2 для новых показаний каждого ДВС, 0 — прежние записи без указания двигателя. История не переименовывается и не удаляется. Для техники с одним ДВС старые показания однозначно используются для её единственного двигателя. Для самосвалов они показываются в форме как прежние показания без номера ДВС и не присваиваются одному из двух двигателей автоматически. Последние показания выбираются отдельно для каждого двигателя по дате и времени записи.

`vehicle_engine_settings` хранит текущие значения `hours_at_replacement` по паре `(vehicle_id, engine_number)`. `GET /api/gto-settings` возвращает их в engines. `PUT /api/gto-settings/vehicles/{id}/engines/{number}` сохраняет показания и значение при замене, проверяет права механика, число двигателей, неотрицательные значения и дату. Для однодвигательной техники ДВС № 2 запрещён.

В PDF самосвал отображается как 875/852 в наработке и 18225/17900 в колонке «М/ч при замене ДВС». Для одного ДВС — одно число. Пустое значение одного двигателя сохраняет свою позицию: 875/ или /852; если неизвестны оба, ячейка пустая. Данные при замене красные. Значения не суммируются и не пересчитываются автоматически.

Старый CSV-импорт сохраняет прежний формат и работает только с engine_number = 0, поэтому он не перезаписывает новые показания ДВС № 1/№ 2. Для самосвалов такие импортированные значения необходимо уточнять отдельно. Миграция `scripts/migrations/20261012_engine_hours.sql` включена в DatabaseInitializer.

## Экспорт в Excel и изображение

В меню «Выход ГТО» доступны «Скачать Excel» (.xlsx) и «Скачать изображение» (.png). Все форматы содержат весь активный парк независимо от поиска: дату и смену, организацию, участок, механика, группы техники, примечания и сводку выхода. Проверка КТГ, права и повтор неудачных сохранений общие с PDF. Длинный отчёт сохраняется ZIP-архивом с пронумерованными PNG-страницами; заголовки таблицы повторяются. В Excel закреплены первые четыре строки, текст переносится, номера строк и КТГ записываются числами; пользовательский текст не исполняется как формула.

PNG создаётся из страниц того же PDF при 300 dpi: шапка, шрифты, цвета, выделения, переносы и сводка совпадают. Ориентация A4 определяется PDF: 3508 × 2480 пикселей для альбомного листа или 2480 × 3508 для книжного. Многостраничный отчёт скачивается ZIP-архивом. Excel получает заголовки, пропорции столбцов и оформленные значения из макета PDF: справа блок ответственных лиц, красные неисправности и моточасы при замене, жирный и курсивный текст примечаний, разделители и сводка. Ячейки остаются редактируемыми; КТГ хранится числом в процентном формате. Печать настроена на A4, одну страницу по ширине, с повторением шапки и нумерацией страниц.

## Хранение и история отчётов

Таблица `gto_reports` содержит `report_date`, `shift`, `revision`, полный `snapshot` в JSONB, `updated_by` и `updated_at`. Снимок не ссылается на изменяемые названия техники или текущие ремонты при чтении. Сохраняется последняя версия каждой даты и смены; отдельного журнала каждой промежуточной правки нет. Таблица создаётся DatabaseInitializer; отдельная миграция — `scripts/migrations/20261022_gto_reports.sql`.

`GET /api/gto-reports?offset=0` возвращает историю страницами по 100 отчётов; `GET /api/gto-reports/{date}/{shift}` — полный снимок. `GET /api/gto-reports/defaults?date=…&shift=…` возвращает предыдущий снимок для переноса КТГ и ТО. `PUT /api/gto-reports/{date}/{shift}` принимает текущую revision и snapshot версии 1. Доступ к чтению — VehiclesView, запись — CanManage. Обновление проверяет revision под транзакционной блокировкой PostgreSQL: при конфликте возвращается 409, чужие изменения не затираются. Проверяются формат, дата, смена, КТГ 0–100, длина текстов и размер запроса до 5 МБ.

«История отчётов» открывает снимок только для просмотра и экспорта, включая весь сохранённый парк. Прошлые даты также открываются только для просмотра. Отчёты, которые не сохранялись до внедрения функции, восстановить из сегодняшних данных нельзя: для отсутствующей прошлой даты выводится сообщение. По команде «Обновить данные ремонта» текущий отчёт получает актуальные данные ремонта с сохранением ручных полей.

При ошибке сети отображается несохранённое состояние и кнопка повтора. При конфликте необходимо открыть серверную версию; локальная резервная копия остаётся в браузере. Переход между отчётами и экспорт дожидаются сохранения; закрытие вкладки с несохранёнными изменениями вызывает предупреждение браузера.
