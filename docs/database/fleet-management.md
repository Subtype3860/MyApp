# Управление парком техники

В блоке «Парк техники» на главной странице доступны «Добавить технику», «Редактировать», «Удалить из парка». Сервер предоставляет управление пользователям с профессией «Механик»/«Старший механик» и администраторам. Обычные работники видят реестр без кнопок управления; прямые запросы изменения получают 403.

Редактор работает с number_car и связанными group_car → type_car → model_car. Обязательны группа, тип, модель и хотя бы один идентификатор машины: гаражный номер, госномер или VIN. Существующие названия доступны в подсказках; новые создаются в той же транзакции. Редактирование сохраняет UUID машины. Изменение модели конкретной машины меняет её ссылку на модель, а не переименовывает модель для других машин. Ограничения длины учитывают текущую базу: названия до 50 символов, госномер до 15, VIN до 20. Непустой VIN (кроме старых заполнителей «-»/«—») не дублируется среди активных машин. Гаражный номер сам по себе не является уникальным: в существующем парке номера могут совпадать у разной техники.

Добавление/редактирование/удаление из парка сериализованы PostgreSQL advisory lock 740410112. Сохранение выполняется в транзакции, включая создание новых справочников. Форма не меняет техническое состояние машины: оно по-прежнему определяется неисправностями и ремонтами.

Физические внешние ключи истории к number_car имеют ON DELETE CASCADE. Поэтому действие «Удалить из парка» ставит number_car.is_archived=true вместо физического удаления. Машина исчезает из активного списка, ремонтов и выбора техники, но UUID, моточасы, закупки, дефекты, работы и медиа остаются. В подтверждении удаления это объясняется пользователю.

Поиск истории и отчёт за смену используют includeArchived=true. Поэтому удаление из парка не исключает работы машины из ранее сформированных периодов. Карточка истории помечает удалённую из активного парка технику. Добавлять новые работы/неисправности через обычные операции для удалённой машины нельзя. Функции восстановления машины в активный парк и физического удаления её истории в этом изменении не добавлены.

API:

- GET /api/vehicles/fleet-options — справочники и canManage, вычисленное сервером;
- POST /api/vehicles — добавить машину;
- PUT /api/vehicles/{id} — изменить активную машину;
- DELETE /api/vehicles/{id} — убрать из активного парка, сохранив историю;
- GET /api/vehicles?includeArchived=true — включить архивные машины;
- GET /api/vehicles/repair-journal?includeArchived=true — включить архивные машины в исходные данные отчёта.

DatabaseInitializer добавляет number_car.is_archived с default false: исходные машины остаются активными. Модели EF дополнены связями справочников, чтобы создание родителей и дочерних записей выполнялось в правильном порядке.

Перед применением сохранена проверенная копия 6 групп, 8 типов, 14 моделей и 39 машин в .local-backups/fleet/20261011T050845Z. Каталог проверен на изолированной схеме с копией реальных таблиц: создание, редактирование без смены ID, сохранность общей модели, запрет повторного VIN, архивирование, сохранение истории и работ в исторических отчётах. Тестовая схема удалена; рабочие записи тестами не изменялись. Браузерные проверки покрывают создание, редактирование, удаление из парка, ошибки прав и телефоны/десктопы.

## Иконки типов техники

`type_car.icon_path` (`varchar(255)`, допускает NULL) хранит путь к SVG для типа техники. API возвращает его как `typeIconPath` в карточках техники и журналах. «Парк техники» использует это поле напрямую: переименование типа не влияет на изображение. При отсутствии пути отображается стандартная иконка.

Файлы размещены в `frontend/public/icons/vehicles/` и доступны по стабильным адресам `/icons/vehicles/*.svg`, одинаковым в разработке и после сборки. Для замены иконки существующего типа достаточно изменить `icon_path` на путь к доступному файлу. Интерфейс загрузки иконок пока не добавлен.

Миграция `scripts/migrations/20261011_vehicle_type_icons.sql` добавляет поле и однократно связывает существующие типы с восемью иконками. Она также включена в инициализацию базы при запуске API. Повторный запуск сохраняет пользовательские пути и NULL. Новые типы создаются без иконки до назначения `icon_path`.
